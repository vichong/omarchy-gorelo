# v0.2.0 full-codebase due diligence

Date: 2026-10-02

Release disposition: the reviewed fixes are included in **v0.2.1**. The assessment and local-acceptance record below preserves what was verified before publication; it does not claim marketplace approval or additional live-write testing.

## Scope and disposition

The assessment covered the **whole production codebase**, including unchanged components, at published v0.2.0 (`7d7a0fceac8c1547c2b5723913c793fbd08bdf3c`). It was not limited to the release diff. Fixes were implemented in an isolated worktree and subsequently reviewed and tested. This report describes those **v0.2.1 fixes**, not the unchanged public v0.2.0 artifact.

Accepted blocking findings are resolved in the tested snapshot. Independent Standards/security and Spec/behavioral follow-ups found no remaining blocker within their reviewed scopes. Lower-severity residuals and unverified acceptance remain below. **This is not a certification, exhaustive audit, or guarantee of safety.**

No live tenant writes, real screenshots, credential inspection, desktop notification delivery, browser control, deployment, commits, new releases or marketplace submission were performed during the isolated review/fix phase described below. Later, separately approved local deployment and manual capture checks are recorded in the follow-up section. The published v0.2.0 tag remains unchanged. Publication requires a separate decision.

## Standards / security

Official Claude Code CLI, Opus 5.5 at high effort, performed independent read-only assessment and follow-ups. Its tools were restricted to file reading/search; it did not run tests. The lead and implementation/runtime lanes supplied separate execution evidence.

| Accepted finding | Resolution and evidence |
| --- | --- |
| Ambient curl config files could weaken transport settings (medium, pre-existing) | Both request and upload invocations put `-q` first. Each regression failed before the change and passed afterward. An offline real-curl probe confirmed config-file uptake without `-q` and isolation with it. API-key disclosure was not exercised. Environment variables still apply. |
| Flag-shaped ticket text could become notification options (low–medium, pre-existing) | Leading-hyphen notification bodies receive a space prefix, retain markup escaping, and cannot match the installed parser's flags. | Timestamped capture filenames could be reused before queued cleanup (pre-existing) | An actual installed capture script, with every desktop effect stubbed, produced the same pinned-time filename twice; real queued deletion then removed the newer synthetic file. Private per-capture staging and random, exclusive final-name publication resolve that reproduction. Process/filesystem regressions and actual Qt integration passed. |
| Localized `stat` file types broke capture, upload and deletion (new capture exposure; inherited attachment issue) | Both helpers scope `LC_ALL=C` to metadata calls only. Portable tests and native German-message probes failed before and passed after. Screenshot/curl children retain their original locale. |

Installed tooltip/dropdown components were inspected and explicitly use plain text. Their earlier potential rich-text finding was not a confirmed defect. This conclusion depends on the installed dependency version.

Optional naming, repeated-literal and duplicated-settlement suggestions were not treated as reasons for a broad refactor.

### Retained low-severity capture limits

- **C2:** interruption before staging identity/cleanup is established can leave private staging artifacts. Unvalidated or unexpected artifacts are not recursively removed.
- **C3:** short startup-handshake windows can refuse capture under heavy load. Failure is now visible and can be retried; no automatic capture retry was added.
- **C4:** cancellation gives the upstream screenshot tool about one second for its cleanup before forced termination. Cursor restoration is not guaranteed if that cleanup stalls.

These limits were reviewed and documented, not silently described as fixed.

## Spec / behavioral

A separate GPT assessment reviewed the whole production behavior, using the approved update plan and README. A fresh reviewer, independent of the implementation author, reviewed the fixes and their follow-ups.

All seven initial failures were reproduced at offline boundaries before fixes:

1. **Account isolation (P1):** different-key submission now invalidates old operations and clears account-specific caches, drafts/screenshots, technician selection, filters and ticket defaults. Startup, same-key submission and ordinary reconnect preserve appropriate state. The user explicitly approved treating key rotation as a new account context; general preferences remain.
2. **Closed local-only search tickets:** retained membership survives filtered-queue removal and empty or failed automatic server refresh without adding unrelated tickets.
3. **Device result union:** a full 200-device server response no longer evicts valid local-only matches merely through historical-cache replacement.
4. **Device freshness:** request-start ordering governs list/query observations; later data replaces older records, and a late older response cannot win.
5. **Draft preservation:** earlier POST/upload/comment completion cannot erase newer draft work or dismiss its overlay. Submitted and newer screenshot lifetimes are distinguished.
6. **Note preservation:** pending duplicate submission is rejected, while later unsent editor changes survive earlier completion.
7. **Actionable errors:** an unrelated ticket's success or action start no longer clears another ticket's failure.

Independent re-review found two additional acceptance defects. Both received failing regressions, minimal fixes and actual Qt follow-up:

- Reconnect during the post-upload screenshot-comment stage now detaches only the consumed attachment reference, preserving text and a genuinely newer screenshot.
- Watched-config tab changes invalidate retained searches and old callbacks, even when filters change simultaneously.

The capture addition also exposed a timeout-feedback regression. Actual internal-helper timeout completion now reports actionable failure for the current draft, without changing its attachment. Empty successful cancellation and stale completion stay silent. The existing QML-deadline message is preserved.

### Approved bounded-search policy

An active query retains up to **1,000 local ticket IDs plus 50 current server IDs**. Existing valid local matches get capacity first and continue updating; overflow local records are not briefly displayed or silently substituted. A distinct warning instructs **clear and search again**. Ordinary automatic refresh does not reset membership. Query, tab and connection transitions do.

Device storage remains bounded: 2,000 base records, 200 historical hits, up to 2,200 active local matches and 200 current server results. No extra server paging was added.

## Other residual risks and release gate

- Forced `SIGKILL` cannot execute traps; private staging, partial output or orphan processes can remain. The capture group has its own deadline, but escaped descendants and orphan collectors are not universally bounded.
- Cleanup checks the opened file's identity immediately before removal; it is not an atomic defense against a malicious process running as the same user between check and removal. Random names prevent the reproduced ordinary timestamp-reuse failure.
- If saving a replacement key fails, the previously stored key can remain in the keyring; a later lookup/retry can reconnect using it, with account settings already reset. Clear failure feedback is not proof that the replacement persisted.
- Queries/IDs can appear in process arguments; the API key does not. The shell holds the key in memory, so a shell core dump could contain it. Inherited curl environment settings remain outside config-file isolation.
- Search/response caps do not establish a total process-memory bound. Large cumulative reference responses, quadratic row reconciliation, very large notification arguments and old curl behavior remain conditional resource risks.
- Ambiguous initial ticket-creation outcomes still lack a verified idempotency/reconciliation contract. A failed or cancelled local workflow cannot prove a sent POST was undone.
- Vendor description rendering, full external process behavior and real status writes/uploads remain unverified. The manual UI/capture follow-up below covers one installation, not exhaustive layout, focus or selector behavior. Direct Connect remains deliberately unimplemented pending a supported public launch contract.

**Summary by axis:** four accepted Standards/security-or-compatibility findings were fixed; three low-severity capture robustness findings remain documented. Seven initial Spec/behavioral findings and three later acceptance defects were fixed. The worst original Standards finding was medium transport configuration exposure; the worst original Spec finding was P1 stale account data. No cross-axis score or claim of universal safety is implied.

These results must not be attributed to the unchanged public v0.2.0 build. The later local deployment below was separately approved; a new release or marketplace request still requires its own decision.

## Follow-up: local deployment and manual acceptance

The operator separately approved a backed-up local deployment of the reviewed worktree, with no commit, public release or marketplace submission. Production source hashes matched the isolated Qt snapshot before and after deployment. No production code changed during the following diagnosis.

### User-reported checks

- Basic panel rendering, search and tab changes, typing/focus, scrolling, and closing/reopening the panel passed.
- Screenshot capture initially failed inconsistently, while draft text survived. After an explicitly approved shell restart, the operator confirmed successful capture and attachment to an unsent draft.
- These are manual reports from one installation, not automated visual assertions. No real screenshot content or private draft text was collected for this report. No live ticket submission, status change or screenshot upload was verified.
- A suggested manual replacement/cancellation check did not match the UI: **Add screenshot** is hidden while an attachment exists; **Remove** intentionally clears it. Do not count that manual check as passed or promise that cancellation restores an explicitly removed attachment. The existing isolated Qt cancellation checks remain separate evidence of draft/file preservation at the service boundary.

### Reload/cache diagnosis

A fresh isolated actual-Button test exercised the Add screenshot handler successfully. Injected busy states reproduced a quiet non-start, but did not establish the live cause.

A separate private Qt reproduction then loaded the old Capture through a symlink, destroyed its instance/component, switched the symlink, and reloaded the unchanged QML URL. It still loaded the old component, twice. A direct URL to the new component loaded the new capture helper. On this installed Qt 6 / Quickshell 0.3.1 combination, `Qt.clearComponentCache` was undefined, so the shell's conditional call did not clear that cache.

This establishes a reproducible stale-component mechanism. The exact pre-restart live Capture identity was not directly measured; the successful post-restart retest is consistent with that mechanism, not proof of every step of the live failure. Disk hashes, symlink targets and a connected status line alone are insufficient runtime-identity checks.

For same-URL checkout switches on affected installations, save/discard drafts, finish pending actions, start a fresh shell runtime and retest the changed behavior. No installed Omarchy source was patched. The README records the deployment precaution.
